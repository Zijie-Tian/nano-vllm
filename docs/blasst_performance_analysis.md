# BLASST 性能分析与密度统计报告

本文档汇总了 BLASST（基于 Softmax 阈值的动态块稀疏注意力）算子的基准测试结果及统计分析发现。

## 1. 稀疏度统计机制：Mask Buffer

我们实现了基于 **Mask Buffer** 的统计方案，用于精准观测算子的行为：
- **原理**：Triton Kernel 在计算过程中，将每个子块的“计算/跳过”决策写入一个布尔矩阵。
- **维度**：`[Query_Blocks, Heads, KV_Blocks]`。
- **优势**：线程安全、无原子竞争、不影响 Autotune、支持多维分析。

## 2. 核心实验：计算密度 vs. KV 需求密度

我们发现，虽然 BLASST 能显著降低 **计算量**，但对 **IO 带宽（数据传输）** 的节省具有挑战性。

### 2.1 统计定义
- **计算密度 (Compute Density)**：实际参与乘加运算的 (Q, K) 块比例。直接对应算力开销。
- **KV 需求密度 (Required KV Density)**：当前 Query Chunk 中，只要有任意一个 Query 需要某个 KV 块，该 KV 块即被标记为“必需”。通过对 Mask 沿着 **Query (Q) 轴求并集 (Logical OR)** 获得。直接对应 IO 传输开销。

### 2.2 实验数据 (GLM-4-9B, 32K Context, Chunk Size 8192)

| Lambda ($\lambda$) | 计算密度 (Compute) | KV 需求密度 (IO) | NIAH 准确率 | 结论 |
| :--- | :--- | :--- | :--- | :--- |
| **0.1** | ~14% | ~28% | 100% | 非常安全，IO 节省显著。 |
| **0.3** | ~11% | ~22% | 100% | 推荐默认值，极致平衡。 |
| **0.5** | ~9% | ~16% | 100% | 较激进，但在 32K 下依然安全。 |

## 3. 128K 超长上下文扩展性测试

在 $\lambda = 0.3$ 的配置下，我们对 128K 序列进行了压力测试：

| 序列位置 | 计算密度 (Compute) | KV 需求密度 (IO) | 准确率 (NIAH) |
| :--- | :--- | :--- | :--- |
| **Chunk 0 (起始)** | ~50.0% | ~100% | - |
| **Chunk 15 (中期)** | ~6.3% | ~14% | - |
| **Chunk 31 (末尾)** | **~3.4%** | **~9.8%** | **100%** |

### 关键发现：
1. **极致稀疏性**：随着上下文增长，BLASST 的优势呈非线性放大。在 128K 处，我们**跳过了 96% 以上的注意力计算**。
2. **IO 瓶颈突破**：在超长序列下，即使是 OR 并集效应也无法阻止 IO 需求的下降。128K 时的 IO 需求降至 10% 以下，意味着**理论带宽节省达 10 倍**。
3. **精度韧性**：即使只用了 3.4% 的算力处理最后的 Chunk，模型依然保持了完美的检索精度。

## 4. 关键技术支撑：LSE 状态解耦传递

BLASST V2 版本的成功核心在于正确实现了 **LSE 状态的跨 Chunk 传递**。
- **原理**：Kernel 接收 `LseIn` 作为全局最大值参考，但计算过程保持局部独立以满足 Flash Attention 合并数学要求。
- **效果**：历史中出现的高贡献块会形成一个“动态阈值屏障”，后续出现的弱贡献块在跨过这个屏障前就会被直接丢弃。

## 5. 调优建议 (基于 V2 算子)
- **推荐 $\lambda = 0.3$**：这是目前在 128K 上下文下验证过的最佳平衡点。
- **生产环境**：务必关闭 `DEBUG_DUMP_BLASST_MASK` 以免磁盘 IO 拖慢推理。
